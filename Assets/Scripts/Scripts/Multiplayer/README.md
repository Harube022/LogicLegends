## Behavior

- Hosts create unlisted, open rooms with six-character cryptographic invite codes and four total slots. The alphabet excludes I, O, 0 and 1. Room-name collisions retry up to five creation attempts. Codes are shown only after joining succeeds; Copy uses the system clipboard.
- Join trims and uppercases the code, validates its alphabet/length, and calls `JoinRoom` rather than creating a room. Submissions are disabled during a request. Full, closed, nonexistent, incompatible protocol and connection failures have readable messages.
- `LL-private-lobby-7` partitions the Photon application version, with PUN's version suffix, so older clients cannot join rooms whose monster selection, counter warnings and recovery behavior they do not have. A room protocol property additionally verifies compatibility. Photon cannot distinguish a nonexistent code from a code in another application-version partition; that error explicitly mentions code, version and region.
- A signed-in player chooses a 3–20-text-element username in the game after selecting a base character. Letters from any language, decimal digits, and `_` are accepted; spaces and other symbols are not. The prompt keeps these rules visible and validates as the player types. It blocks common abusive English and Filipino terms, including simple number and accent substitutions. Returning Google or email accounts with a character but no valid username see the same prompt before entering the menu. The name is saved at `users/{uid}/username`; the Google account name is never used as the Photon nickname. The lobby, chat, and MultiplayerStage avatar nameplates use that username, with an Adventurer fallback if a profile is unavailable. Actor numbers, not names, identify roster/readiness/chat senders. Duplicate usernames are currently allowed. The client filter cannot guarantee moderation of every inappropriate name or direct database writes; production enforcement belongs in trusted server-side account validation.
- All players initially join Not Ready. Ready is a Photon player property. Only the current Master Client can start, with 2–4 present players all ready. Starting closes the room, uses conditional waiting/locking/loading properties, waits for server state and rechecks readiness/membership before `PhotonNetwork.LoadLevel`. Membership changes before loading cancel the start. Full rooms never start automatically.
- The destination is configurable on the main-menu NetworkManager's `MultiplayerMenuManager`; the completed **Open Archive MultiplayerGameplay** scene is the default. Lobby routing reuses its existing puzzle, encounter and completion systems.
- Room chat uses reliable Photon room event 74. The shared English/Filipino filter masks common abusive words before sending and again before adding received messages to history; both the waiting lobby and MultiplayerStage chat use this service. Empty and over-200-character messages are rejected, sending has a one-second cooldown, receiving applies a per-actor rate limit, and visible history is capped at 60 entries. TextMeshPro rich text is disabled for history, names and input. Join, leave and host-change messages are local system entries. No chat is written to Firebase; late joiners start with fresh local history. This client-side filter is not comprehensive moderation of messages sent by modified clients.
- Deliberate leaving clears room/chat state and removes the actor immediately. Unexpected recoverable connection loss keeps the scene and attempts to rejoin the same actor, as described below. Idle menu connections are disconnected on solo entry and cannot redirect a solo stage later.

## Connection recovery — 2026-10-21

The existing lobby service owns recovery in both the waiting lobby and Open Archive. After a recoverable transport disconnect it shows RECONNECTING, blocks only that client's controls, and attempts the original token-based room rejoin for at most 30 unscaled seconds and four attempts. The room reserves inactive actors and empty rooms for 45 seconds, allowing margin for timeout detection and handshake. Recovery never joins as a fresh actor, creates a new room, opens a started room, or steals authority from the newly elected Master. Explicit Leave Match and app quit do not retry. Fatal authentication/protocol errors and missing/expired slots return a readable reason.

PUN's cached Instantiate replay restores the original avatar/view ID. The returned actor is verified before the existing exploration binder and camera are reattached. A bounded four-avatar position checkpoint is published by the current Master at most once per second. Owned avatars suppress outgoing serialization until restoration completes, preventing a temporary replay of the original spawn position. Health, topic progress, mistake attribution, clocks and barrier outcomes use their existing authoritative room checkpoints. A newer live monster snapshot takes precedence over an older periodic checkpoint.

Inactive actors retain health and hunting history until their reservation expires; they cannot interact, be selected for a new hunt, or take over local input when the Master becomes controller of their PhotonViews. They still count toward the existing all-survivors exit requirement. A captured actor keeps the original challenge deadline and restrictions through a reconnect. Connected teammates continue normally, and online Settings no longer sets the whole simulation's time scale to zero. PUN also dispatches at time scale zero for other overlays that may pause Unity.

`NetworkDiagnostics/latest-disconnect.json` under `Application.persistentDataPath` contains at most 32 recent samples: RTT, jitter, reliable resends, queue sizes, frame stalls, time scale, reachability and pause/focus state. It records the transport, original cause, retry cause and recovery result. The file is replaced per outage and contains no invite code, account ID, authentication token or chat. Android uses the app-specific files directory. This instrumentation does not establish that the mobile carrier caused a timeout; compare the recorded transport, focus and frame data.

Run **Logic Legends > Multiplayer > Run Connection Recovery Checks (Play Mode)** from Main Menu for private-room loss/rejoin validation. The independent editor control peer uses a longer test-only transport timeout to tolerate editor stalls; production timeout settings remain unchanged. Physical mobile networks, OS suspension and process termination still require device tests.

## Close-range circling counter — 2026-10-21

The existing host-owned hunting controller turns smoothly toward the actual target at close range, up to 300 degrees per second. Sustained tangential player movement within the close-pressure distance must accumulate 1.8 seconds and 80 degrees before the counter starts. Standing nearby, a brief dodge, the monster's own translation, water pursuit and movement during cooldown do not build a counter. Normal pursuit speeds and normal capture distance are unchanged.

The counter reuses each rig's existing Attack clip: 0.6-second warning, 0.35-second strike, 0.8-second recovery, then a 3.5-second cooldown. A colored ground arc and the existing spatial growl announce it. Rajang has a 160-degree sweep; Khezu has a 90-degree strike and at most a 3-unit lunge. The aim stops tracking when the strike starts. Navigation and physical obstruction checks constrain the lunge. Capture requires the selected target to remain in the active strike window, inside the short surface reach/arc and in clear upper-body sight. Distant targets, solid walls and platforms above the monster's body remain protected. A miss suppresses ordinary captures through recovery.

A hit calls the existing capture path exactly once, followed by the existing POV jumpscare and barrier challenge. The counter does not remove a heart. The same encounter, health and no-repeat hunt rotation stay in charge. Counter phase, serial, fixed aim, timing, cooldown and lunge progress travel in the existing validated snapshot and room checkpoint. An authority handover cannot replay an elapsed strike. Peers render the warning locally from those timestamps; no second gameplay controller or network object is created.

Inspector tuning is under **Dodgeable close-range counter** on the existing KhezuHuntingController. `Resources/Multiplayer/CloseCounterWarning.mat` keeps the URP material available in builds; presentation uses one pooled line renderer and one spatial audio source per encounter. `MonsterCloseCounterPlayChecks.Begin()` is an opt-in Editor-only native test under the existing testing folder. Its report covers both rigs and the normal cinematic/barrier handoff; real remote devices and Android frame/network latency remain unverified.

Latest native verification: **35/35 checks passed, zero Unity errors**. The checks include selected-rig palettes, Rajang's stationary sweep, Khezu's measured 3-unit lunge, sustained-circle triggering, warning timing, a committed aim that can be dodged, recovery/cooldown, snapshot timing, blocked/distant/high targets, a single capture without heart damage, and the normal cinematic/barrier handoff.
